# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| `diagnosis-grounded` | The candidate plan's stated cause or diagnosis, read against the repro-evidence block (steps, artifacts, control runs) and the issue body's described behavior. | The stated cause is consistent with what the repro evidence actually shows: it explains the failing artifact, and does not contradict a control run or measurement in that same evidence that rules the cause out. Fail when the plan blames a component the evidence's own controls already cleared, ignores a decisive control, or invents a cause with no footing in the shown steps/artifacts. | required |
| `scope-bounded` | The candidate plan's in-scope / out-of-scope statements, proposed changes list, and named files or areas, read against the issue and the repro-isolated defect. | The plan commits to one bounded change that addresses the reproduced defect (or an explicitly scoped-down slice of it with reasons). Fail when the fix is wrapped in a redesign, migration, cross-construct rewrite, new option/framework, multi-runtime abstraction, or other while-in-the-area campaign the issue did not ask for — even if a correct core fix is buried inside. | required |
| `executable` | The candidate plan's chosen approach, named files or areas, and ordered steps a builder would take. | A stranger could start the build without asking the author what to change: at least one concrete file/area and one chosen approach are named. Fail when the plan only says "investigate", "profile and optimize", "recover() somewhere", "upstream or vendored, whichever is easier", or otherwise defers every real decision to build time with no files and no chosen layer. | required |
| `test-decisive` | The candidate plan's test plan, read against the repro-evidence steps and expected/actual behavior. | The test plan names an observable outcome for the fix itself (exit code, redacted string, color flip, panic gone, specific assertion) by re-running or adapting the repro steps. Fail when success is only "should feel fast", "nothing else should feel broken", "run the full test suite" with no fix-specific observable, or any outcome a stranger cannot check against the issue's behavior. | required |
| `thread-aware` | The candidate plan comment (and plan approach) read against Thread highlights when they contain an OWNER/maintainer direction, culprit file, patched binary, or explicit preferred fix path. | If the thread has no such maintainer direction, pass. If it does, the plan and comment engage that direction (follow it, or name a concrete reason to diverge). Fail when the comment/plan ignores an explicit culprit location or owner-posted patch path and substitutes an unrelated workaround (e.g. docs-only) without addressing the thread. | required |
| `ai-disclosure` | The repo-facts contribution / AI policy line, plus the candidate plan comment text. | If the policy requires disclosing AI usage, the plan comment discloses the tool and that a human reviewed/verified the work. If the policy is silent, permissive, or has no disclosure rule, this check passes. Course packages are treated as AI-assisted whenever disclosure is required. | required |
| `honest-unknowns` | The candidate plan's risks, unknowns, and confidence language, read against how much the repro evidence actually settles. | Open questions are labeled as unknowns or deferred work rather than stated as settled fact. Preferred only: a terse plan with no risks section still passes if it does not assert false certainty. Fail (preferred miss) when the plan treats an unresolved choice as already decided with certainty the evidence does not support. | preferred |

## Verdict rule

Accept only if every `required` check grades `pass`. Any required `fail` or `unclear` makes the verdict `reject`. Preferred checks never change the verdict. Treat `unclear` as `fail` for required checks: a plan you cannot verify from the package is not ready to build from.
